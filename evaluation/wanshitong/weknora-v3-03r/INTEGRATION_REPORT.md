## 修正与归因

只进行了一轮代码修正：

1. 自然问答输出上限由 2048 调到 2680。配置的估算输入上限 5000、输出 2680、安全余量 512 相加为 8192；没有缩短检索材料，也没有加入针对某题的答案规则。`estimated_input_tokens` 不是 Provider 实测用量；本次 Qwen SSE 未返回可用 usage。
2. Provider 流式合同若报 `CHAT_OUTPUT_TRUNCATED`，在 transport 与管理员安全诊断中保留这个内层原因，不再泛化为 `INVALID_STREAM_SCHEMA`。临时私有捕获只在显式启用时保存已消费响应，普通 Trace 不写模型正文。
3. 共享 SSE 解码器未放宽 `reasoning_content`、工具调用、重复 usage、缺失 `[DONE]` 等合同。服务器关闭思考模式；本轮直连实测的 `reasoning_content` 长度为零。

原 P0 的三次 74—75 秒失败来自较早镜像，原始 SSE 已不可取得，故不能证明其唯一根因。独立合成长输出在 2048 上限、约 74.08 秒时真实返回 `finish_reason=length` 与 `[DONE]`，说明截断是该模型配置的实际可能路径。相同文档和原 P0 问题在本轮 2680 上限下正常收到 `stop`；但把本轮冻结的同一送模包只调回 2048 后也收到 `stop` 和 `[DONE]`。因此，输出预算扩大是有依据的通用余量修正，**不能据此认定旧 P0 一定是额度不足**。
