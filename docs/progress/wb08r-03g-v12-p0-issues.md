## P0-01：明确命名的来源没有成为确定性回答边界

**实际观察**

- F024 冻结行为为 `REFUSE`，实际为 `ANSWERABLE`。
- 题目指定了一个明确文档，最终四条引用全部来自另一文档，
  `expected_source_in_citations=false`。
- 批量语义复核把该 Claim 判为可发布，最终命中 `SAFE_REFUSAL`、
  `WRONG_SOURCE_SEVERE_ERROR_COUNT`、`TEMPLATE_BODY_OVERREACH_COUNT` 和
  `UNSUPPORTED_HIGH_RISK_FACT_COUNT`。
- C1 的 F024 已出现同类错误；C2 只是被预算挡住，并未证明该语义问题消失；C3 解除
  预算后同类错误再次出现。

**根因判断**

查询中的文档限定只参与语义理解或检索排序，没有成为生成前的确定性来源所有权约束。
模型因此可以拿“主题相近但文档不同”的表格行回答。第二个同模型语义调用不能替代服务端
的文档身份核对。

**恢复要求**

1. 查询计划显式携带 `required_document_identity` 或可解析的来源限定；无法唯一解析时走
   澄清或拒答，不得静默退化为全库检索。
2. Evidence admission、Wire 的 `allowed_ref_ids`、BoundClaim 和发布前绑定均验证同一
   文档限定；不相符的 Support 不得进入该 Atom 的允许集合。
3. 增加通用成对测试：指定文档存在/不存在、同名近似文档、模板目录项与其他实施方案、
   正确文档和主题相近错误文档同时召回。
4. F024 固定回放必须稳定拒答；不能通过写 case ID、文件名白名单或业务关键词特判实现。

## P0-02：问句仍能向 Claim 注入来源没有陈述的关系

**实际观察**

- N031 的三次答案摘要完全一致。
- 来源只明确表格行、列名“输入”和若干输入值，输出却把它改写为前置时序义务。
- C2 已规定 question/Atom 不是证据；C3 又明确禁止从问句带入时序、条件和义务，
  但真实模型仍生成该关系，批量语义复核仍判为支持。
- 三次人工判断均为 `UNSUPPORTED_HIGH_RISK_FACT_COUNT=1`。

**根因判断**

当前 Wire 只绑定“用了哪些阅读单元”，没有绑定“Claim 中哪个谓词由来源的哪个关系
锚点证明”。对自由文本 Claim，生成模型和复核模型都会受问句措辞影响；继续追加同义
提示无法形成硬保证。

**恢复要求**

1. 为结构化来源提供服务端关系锚点，例如 `row_label`、`column_label`、`value` 和
   `relation_kind`；自由字面片段不得获得未闭合的关系种类。
2. 表格 Claim 应先绑定到明确关系，再自然渲染。列名为“输入”时，可发布“输入包括…”，
   不能仅因问题含“前”就发布“之前必须…”。
3. 语义判定必须返回并校验 `supported_relation_anchor_ids`，只返回 supported/unknown
   枚举不足以证明关系来源。
4. 使用“输入/结果/负责人/时限”与“之前/之后/必须/可以”的成对反例；正例和反例要在
   同一实现中同时通过。

## P0-03：同一模型生成后再自审不能作为零严重错误门槛

**实际观察**

- C3 每条可回答请求均进行一次生成和一次批量语义复核，共 32 次 generation 调用。
- F024 的错来源 Claim 和 N031 的无依据时序 Claim 都通过了该复核。
- P0～P3 合成语义检查 12/12，但真实 Preflight 仍出现上述错误。

**根因判断**

复核已经替换了旧的词面硬门，这是正确方向；但当前复核与生成使用相同模型、相近上下文
和相同问句诱导。它能过滤一部分错误，不能被当成独立真值裁决者。合成 happy path 也没有
覆盖“主题相关但指定来源错误”和“列名相关但关系强度错误”。

**恢复要求**

- 先由服务端完成可独立验证的来源、版本、文档限定、关系锚点和引用所有权检查，再调用
  模型处理自然语言等义。
- 复核请求只允许判定已有锚点是否覆盖 Claim，不得用问题补齐缺失关系。
- Trace 至少记录不含正文的 Claim hash、所选关系锚点、来源文档身份 hash、复核 verdict
  和拒绝原因；不得只留下 `SEMANTIC_REVIEW_VALIDATED`。
- 在 F024/N031 回放未稳定通过前，不得把复核调用增加到第二轮或恢复 repair。

## P0-04：部分发布与“完整回答”验收仍未闭合

**实际观察**

- C3 的 F015 只覆盖问题中的输入内容，未覆盖同题要求的启动条件，并明确显示未完整组织；
  冻结行为却是 `ANSWER`。
- N033 只发布了一个有来源的安全职责片段。该行为比旧版整题清空安全，但不等于完整答案。
- 本轮在 F024/N031 确定失败后停止，其余 12 条没有完成正式人工事实裁决，因此不宣称
  F015/N033 或其他答案已通过质量门。

**恢复要求**

- 服务端按 Atom 记录 `ANSWERED`、`UNANSWERED` 和拒绝原因；渲染可发布安全部分，但 Gate
  必须按冻结的 `ANSWER`/`LIMITED` 语义分别验收。
- `ANSWER` 必须覆盖全部必答 Atom；`LIMITED` 才允许明确的部分回答。
- 不得用“有一条 Claim、有引用、显示未完整”替代问题覆盖率。

## P0-05：同物理行合并解决了预算，不证明该行与问题相关

**实际观察**

- C2 F024 的 8 个 Support 来自两个物理表格行，按 8 个阅读单元发送，语义复核最坏预算
  无法容纳，任何生成前即 `BUDGET_BLOCKED`。
- C3 将每个物理行分别合并为阅读单元，保留全部 Support ID 后，生成与复核均成功发送。
- 解除预算后，错误来源的行反而被模型用于形成 F024 答案。

**判断**

合并是正确的传输优化，应保留；它不授予相关性或语义证明。下一步不能撤销合并、扩大
token 上限或重新丢弃全部表格字面证据，而应在发送前解决来源限定和 Atom 关系所有权。

**回归要求**

- 同一物理行合并后 Support ID、跨度、文档版本和顺序必须完整保留。
- 不同表、不同行、缺坐标片段不得合并。
- 合并后的 `literal_table_fragment` 仍保持 `table_relation_complete=false`。
- F024 的错误文档行不得进入该 Atom 的 `allowed_ref_ids`。

## P0-06：三轮达到上限，剩余样本不能被包装成通过

**实际观察**

- C3 reviewed summary 为 FAILED；两个决定性模式已人工绑定问题和答案摘要。
- 其余 12 条保持 `MISSING_FACT_REVIEW`，没有以自动指标补成人工通过。
- A～F 均未运行；生产未修改；8289 已回滚基线。

**恢复要求**

新的工作必须被视为新的架构修复批次，而不是 V12 第四轮微调。开始前至少提供：

1. 通用的明确来源限定合同；
2. 可验证的关系锚点合同；
3. F024/N031 失败回放及对应正反例；
4. 不依赖新增业务词表或 case 特判的实现说明；
5. 新的候选次数和停止条件。

满足上述条件后，仍按 P0～P3、Preflight-16、EvidencePack-12、CoreAnswer-16、
Failed-24、Natural-36、Full-96、Concurrency-4 的顺序执行。任一前置 Gate 失败即停止后续。

## 冻结结论

V12 的统一 Wire、服务端引用恢复、批量语义复核、正常资料不足终态和同物理行压缩均有
保留价值。当前 P0 不支持回到旧词面硬门、增加 retry/timeout、扩大输入上限、恢复默认
repair、换向量库或推倒检索链。

真正未闭合的是两条通用契约：**指定来源必须成为确定性所有权边界；自然语言关系必须能
指向来源中的关系锚点。** 在这两条有固定反例证据前，不再生成新的 8289 候选。
