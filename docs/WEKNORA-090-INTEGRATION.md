# WeKnora 0.9.0 与湾小度的融合方案

## 版本与阶段

- 上游固定为 v0.9.0，提交 `f17ee8a8da901bd658a4cb25f40b5fd41adbfdd7`，不跟随 main。
- 0.9.0底座升级及历史功能只在8289；模型池和问答准入配置按用户后续授权同步8288，生产资料与入口规则保持。
- 2026-11-01 已在 8289 完成 0.9.0 升级、真实登录与权限/问答验收；8288 仍为 0.8.3。
- 图片管线设置已接入；只读助手、协作和自动化已完成身份及权限适配。54/57/58共五路现有8B均为24576，经60模型池接入8288和8289普通问答。五路联合20条长输入全部成功、模型端同时运行10条；两个网关均为8条运行、8条等待，并分别通过8条真实知识问答验收。跨文档对比和部分工具使用质量仍未通过，工作助手、协作和定时任务入口继续关闭。
- 本文集中记录新增能力的接入边界；实际部署与验收状态以对应部署记录为准。

## 底座收益与数据处理

0.9.0 的直接收益包括图片处理管线、Office/PDF 解析保真、资源复用、
引用定位、流式错误处理和检索兼容性改进。这些收益不要求开放原生助手。

- 保留当前模型、知识库与文档标识，沿用已有文件和向量；不因升级全量重建或重解析。
- PostgreSQL 新增迁移 000119–000134；其中 000125 清理符合条件的空图片派生分块，
  不删除源文档或文件。该清理不由 down 恢复，回退依赖升级前备份。
- 图片预处理、Excel 百分比文本等新解析选项只影响新上传或主动重新解析的资料。
- 需要新解析效果时，先挑选对应文档验证，再决定是否重新解析；不批量处理正常资料。

依据：[官方版本与升级说明][release]、[空图片分块迁移][empty-images]。

## 本轮定向接入

### 图片管线：在现有管理后台使用

使用上游 `image_processing_config.image_pipeline`，提供两种原生选择：

| 管线 | 用途 | 本轮边界 |
| --- | --- | --- |
| `default` | 手动选择图片描述、OCR | 沿用原生开关及校验，不增加本地识别流程 |
| `smartocr` | 先观察图片，再决定是否 OCR | 按知识库显式选择，不自动替换所有旧配置 |

- 目录与配置校验仅定向放行 `GET /api/v1/image-pipelines` 和
  `POST /api/v1/image-pipelines/validate`；校验不触发文档解析或模型生成。
- 配置仍通过已有知识库设置保存，原有资料归属检查继续生效。
- 普通管理员仍不能读取或修改人力内部库；人力角色不因此获得全局管理后台。
- 参数按管线保存，例如 `default.caption_enabled`、`default.ocr_enabled`；
  未显式保存新管线的知识库保留上游对旧 `image_attrs_enabled` 的兼容。
- 文档照片矫正、裁边属于可选预处理，默认关闭；开启后仍需单独验证目标图片效果。

依据：[原生图片管线说明][parsing]、[管线参数命名与兼容规则][pipeline]。

### RRF：使用原生检索设置

在已有后台检索设置中使用原生 `rrf_k`、`rrf_vector_weight`、
`rrf_keyword_weight`，由 `tenants/kv/retrieval-config` 保存。
网关不另写融合、重排或召回算法；参数只影响排序，不扩大允许检索的资料集合。
本轮不因新增界面而主动调整所有参数；如需调优，使用明确问题比较引用及回答。

依据：[原生 RRF 设置接口][rrf]。

## 助手、协作和自动化的身份适配

当前普通问答通过公共 API Key 和签名的 RDMS 用户标识建立原生会话；
资料分区由湾小度 `LibraryService` 判断，管理操作通过共享原生管理员账号执行。
这与上游新增能力要求的“原生 Web 用户本人身份”并不相同。

1. 上游 operations 只接受真实 `WebUser`，明确拒绝 API Key；多智能体父任务也
   使用该身份检查，子任务恢复时重新读取原生用户及工作区成员身份。
2. 自动化接口未向 API Key 开放；后台按原生 `OwnerUserID` 重建执行身份。
   直接使用共享管理员账号会让多位 RDMS 用户的任务、历史和审批归到同一人。
3. 同原生 tenant 内的知识库按工作区资源授权，不能表达现有“个人资料仅本人”
   和“人力内部仅人力及超管”的全部规则；仅新建原生用户仍不足以替代网关授权。
4. 内置助手的页面上下文不会自动缩小知识范围；未显式限制时可使用工作区范围。
   `read_only` 只限制写操作，“修改前确认”只表示同意，二者都不能代替资料授权。
5. 原生工具在后台直接执行时，不会再次经过当前网关的 HTTP 资料检查。
   不能靠隐藏按钮、提示词声明或共享管理员令牌完成权限适配。

为保留这些约束，本轮增加独立的只读工作助手，不替换现有 quick-answer 问答：

- 每位研发系统用户对应独立原生 WebUser；每个“用户 + 所选资料范围”建立独立工作空间。服务账号拥有空间，员工只持有 Viewer，浏览器不取得原生 JWT。
- 原资料和ID留在源空间，通过不可搜索的专用组织把允许的知识库以 Viewer 分享给目标空间；不复制或重新解析原资料，也不把员工加入源空间。
- 资料集合由 `LibraryService.search_kbs` 计算。公共、个人、人力内部及其组合分别隔离上下文；集合变化后关闭旧一代，禁止复用其会话。
- 内置助手的资料工具仅保留搜索、读文档和列文档，使用精简资料助手提示和1024输出预算。原生另行注入的管理、产品文档和协作工具仍受原生只读及Viewer权限约束；禁用外网、MCP、技能、记忆和沙箱。原生协作子任务继承父任务的只读资料范围，不能选用扩大范围的模板。
- 自动化归本人，强制 `read_only`、`session_mode=per_run`、`carry_last_result=false`。创建、记录、取消和通知仅经本人空间的定向接口，不提供任意原生代理。
- 每个请求和流事件重新核验当前身份。收紧人力权限前先禁用空间，暂停定时任务、取消运行、停止助手，再撤 Viewer 和组织成员，最后保存业务角色；撤权失败时不保存降级。
- 公共资料绑定变化前撤销受影响空间。普通关闭进程不删除用户定时任务，避免升级时误清正常任务。

这些能力由 `WXD_WORKBENCH_ENABLED` 显式控制，默认关闭。原生账号和空间创建只在服务端初始化，普通管理后台仍不挂载原生助手、自动化或平台管理入口。

真实预演已验证两个用户、独立空间、私有与公共隔离、Viewer 自动化创建/暂停/删除、人力降权后停任务和撤成员，共57项HTTP检查。用户随后明确批准共享模型维护，已增加自动工具选择和hermes解析器；结构化工具调用、工具结果回传、普通对话和8288实际问答均通过。

最初54模型的真实助手在首次调用即超出8192上下文，用户当时选择保持8192，随后先用57/58独立验证24K。用户最新明确要求54也接入、两个环境同步后，54才扩至24K并加入共享池。没有靠虚增模型元数据绕过真实上限，助手任务质量未通过的问题仍单独保留。

### 模型池实测与并发边界

57/58各有4张10GiB RTX3080，每两张以TP=2运行一份Qwen3-8B-AWQ；54再复用GPU0/1上的一份同型模型，共五实例。首次候选先在58:8001配置自动工具选择、hermes解析及24576上下文，随后逐路扩展到其余实例。显存预算0.82、单实例并发2不变，没有下载新权重或修改Go检索算法。

- 结构化工具调用、流式工具调用、工具结果回传和超过8K输入的真实生成均通过。
- 默认keyword检索出现ParadeDB `Unsupported query shape`。仅候选工作区指定原生semantic模式后可检索正确资料；具体SQL子句原因尚未隔离，不能把绕开错误算作修复。
- 菜单题及同会话续问正确；跨文档对比未充分读取，内容对应不准。协作创建和等待正常，但子任务未完全遵循读取要求。当前不能仅凭任务completed宣称答案质量达标。
- 普通用户个人资料与超管人力内部资料同时问答均正确，耗时6.36秒和6.17秒；检索结果各限于本范围。另有14项既有资源权限核对和6项合成资料跨范围读检查通过；本轮没有重新执行人力角色降权验收。
- 四条各21814输入token的合成请求同时提交，单实例实际最多同时运行2条，其余排队；全部HTTP成功，耗时32.80–66.18秒，KV占用峰值约70.3%，无KV抢占及显存溢出。每条人为限512输出token、均以length结束，这只证明容量和排队，不代表长答案完整性。

每实例实际KV容量为63552 token。两条24K完整序列需要49152 token，可以容纳；四条需要98304 token，无法保证单实例全部驻留。因此采用五实例各2槽位，通过60:18098的Nginx least_conn分流。最新联合20条各约21800输入token、256输出上限的请求，五实例各承担4条，实际峰值10条同时计算，其余排队；20条均成功，整批45.40秒，KV峰值约69.5%。该批人为限输出并以length结束，只验证容量，不代表完整长答案或长期压测。单实例没有为凑4槽位而缩窗。

8288和8289普通问答均已接入模型池，并同步设置 `WXD_QA_MAX_ACTIVE=8`，每环境8条运行、8条等待；代码未配置此变量时仍默认4。五路10槽位由两环境及其他既有调用共享，不是每环境独占8或10路。两个环境分别进行8条完整知识问答并发，ops运行峰和流重叠峰均为8，菜单及目标引用、Trace/原生历史均正确；没有声称两环境同时16条完整问答已经实测。当前内外网地址、知识库权限、公开agent/model ID、普通问答2048输出设置均保持。

此前“四并发”指网关可同时处理4个问答流程，流程包含检索及等待模型，不代表4条都在模型计算。仅用54时模型执行容量为2；57/58阶段为8；当前五模型为10，入口则统一8。登录人数也不等同正在生成的请求数。

资料范围由现有授权服务及原生Viewer分享限制，不随模型端点数改变。并发槽位是同时计算的模型请求数；协作会产生额外子请求，不能直接等同在线用户数。

本轮临时资料、会话和任务均已清理，11个候选工作区禁用并撤权，私有候选网关已移除。五路保留24K及工具配置；8289正式工作助手仍关闭。完整实测、历史删除/归档发布及生产接入见[实施记录](V2-8289-IMPLEMENTATION.md)。

### 暂不开启工作助手的结论与问题总结

**当前阻塞是检索兼容和任务执行质量，现有显卡容量已经通过本轮定向实测。** 增加模型实例能提高吞吐，并不会自动纠正工具选择或材料理解。

| 问题 | 已有证据 | 判断与后续方向 |
| --- | --- | --- |
| 原8192窗口不够 | 内置工具说明在首次调用即超限；24K后能真实搜索、读取、协作 | 属于上下文配置限制，现54/57/58五实例已统一24K |
| keyword检索SQL报错 | ParadeDB Unsupported query shape；semantic模式可检索 | 属于上游查询兼容问题，与增加模型参数或显卡无直接关系；需定位或明确限定语义模式 |
| 工具读取与对比不可靠 | 只读开头、重复相同分块、未按要求读全文，对比要点对应不准 | 本轮8B助手配置未达标；可能涉及提示、工具使用及模型能力，不能仅凭参数量断定换大模型必然解决 |
| 显卡是否需要更换 | 五路24K、20条并发提交、10条同时计算通过，单卡采样峰值约8.2GiB/10GiB | 当前无采购依据；保留现有硬件。待检索/工具问题明确后，再用同一题集比较更大模型是否值得 |

工作助手、协作入口和定时任务暂不启用，普通问答继续运行。以后若开展灰度，应先以明确资料范围的单文档整理和菜单题通过验收，再扩展到跨文档对比；不把普通问答成功或容量通过当成助手任务质量通过。

依据：[操作身份检查][operation-identity]、[协作身份恢复][collaboration]、
[自动化接口边界][automation]、[同 tenant 授权][kb-access]、[助手资料范围][assistant-scope]。

## 沿用的权限矩阵

公共资料包含公开人力制度。所有角色的问答默认选择公共资料；个人或人力内部范围
由用户明确选择。超级管理员以 `admin + is_super_admin` 表达，不新增第四种普通角色。

| 身份 | 可选问答范围 | 资料维护 | 用户与角色 |
| --- | --- | --- | --- |
| 普通用户 | 公共、本人个人资料 | 本人资料及本人主动共享的副本 | 无 |
| 人力 | 公共、本人个人资料、人力内部 | 本人资料、公开人力制度、人力内部资料 | 无 |
| 管理员 | 公共、本人个人资料 | 公共及现有授权的个人资料管理；不含人力内部 | 普通/人力角色，不能任免其他管理员 |
| 超级管理员 | 公共、本人个人资料、人力内部 | 全部现有授权资料管理 | 管理员任免及其他角色管理 |

- “管理员可管理个人资料”不自动变成“问答可搜索其他人的私库”。
- 普通管理员之间不能互相降级；不能修改自己的角色或受保护的超级管理员身份。
- 人力内部权限只认当前人力身份或超级管理员；普通管理员不继承该权限。
- 既有会话、引用、图片和下载同样受资料权限检查，不能通过旧记录扩大访问范围。

## 接入状态与启用条件

### 阶段一：完成当前底座升级

仅接入上述图片管线及原生 RRF 设置，保留已有登录、资料选择、历史与权限行为。
针对图片配置保存、文件解析、引用图片、普通用户私库和管理员的人力隔离进行验收。
已完成 7 个候选问答场景、跨角色访问检查、新 DOCX 图片解析及临时知识库图片配置保存回读；最终入口重新完成两个真实账号的 CAS 登录、旧会话续问和图片读取。全部原 100 份资料、310 个原文件及旧会话/消息标识均保留，具体证据见[实施记录](V2-8289-IMPLEMENTATION.md#2026-11-01-8289-升级-weknora-090)。

升级不保证所有回答和图片问题自动消失。预演曾出现正确引用个人测试文档、但模型抄错随机校验码的情况；原始引用中的校验码正确，未改动模型、提示词或算法。继续按实际引用和回答内容判定质量，不能仅凭请求 completed 判定答案正确。

### 只读工作助手：适配完成，等待任务质量验收

员工界面增加独立“工作助手”，可整理和比较所选资料、查看协作进度，手工创建只读定时任务。入口只随服务端能力标志显示，默认公共范围；切换范围先卸载旧工作区再连接新空间。主题跟随问答界面，失败时可重试。

启用前仍需解决或明确规避关键词检索兼容问题，并用实际模型通过文档读取、资料对比和协作结果验收，再验证跨用户及撤权行为。定时任务按用户当前决定暂不启用，之后需要时单独验收。接口CRUD、任务completed和容量通过不能替代答案质量。真实8289点击与视觉验收仍另列待完成，本轮只进行了私有接口测试。

### 后续写操作：不在本轮范围

上传、删除、共享和用户角色调整继续使用现有业务入口。工作助手不自动发布公共资料，也不能修改角色或资料；后续只有明确业务需求才接入少量写操作，仍复用原有资料服务及超管规则。
